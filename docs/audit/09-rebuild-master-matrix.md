# Status legend

## KEEP
Supported and useful. Preserve the underlying fact/asset, although presentation may be redesigned.

## REWRITE
The subject belongs on the site, but current wording/structure is weak, inaccurate or template-like.

## REMOVE
Unsupported, misleading, obsolete, duplicate, unrelated or technically inappropriate.

## VERIFY
Potentially genuine/useful, but requires owner/primary documentation before publication.

# 22. Source-of-truth hierarchy for rebuild

When conflicting information appears, use this priority:

1. current owner/company documentation;
2. current packaging/product master data;
3. legal/company records;
4. official/current company platforms;
5. HFZA / reputable press / direct executive statements;
6. historical official regional stores;
7. established media/directories;
8. current prototype — **never use as evidence by itself**.

# 26. Final audit decision

The existing Caline project should be treated as:

> **a useful archive of a previous design attempt and a holder for the authentic logo/domain — not a trustworthy product database or a suitable production design foundation.**

The rebuild should preserve:
- domain;
- authentic identity;
- verified manufacturing history;
- relevant historical evidence.

It should replace:
- layout;
- imagery;
- catalogue;
- content hierarchy;
- navigation;
- ecommerce implementation;
- SEO/accessibility foundation.

Research and planning are now sufficiently complete to begin a professional rebuild **without repeating the mistakes of the current prototype**.

## Stage 10 — Implementation gate

**No public site code should be changed automatically at this point.**

Before Stage 10 begins, choose the implementation scope:

### Option A — Corporate + catalogue first
Professional new site with verified company content and product architecture; ecommerce added when real product data is ready.

### Option B — Full ecommerce rebuild
Requires the current authoritative product catalogue, pricing, logistics and payment decisions before the store can be completed correctly.

In either case, implementation should preserve all files in `docs/audit/` as the project decision record.
